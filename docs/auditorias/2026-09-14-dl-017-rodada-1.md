## Achados

### 1 — ALTA · `NaN`, `Infinity`, `1e500` digitados no campo de valor derrubam a tela com 500

**Requisito:** critério 13; AGENTS.md §8 ("validar entradas nos limites do sistema", "não converter falhas em sucesso aparente"); `docs/projeto/decisoes.md` DE‑010.
**Local:** `/home/user/DataLedger/apps/contabilidade/views_web.py:124` e `:129` (`_valor_ptbr`), alcançado de `:617` e de `:461-462`.

**Reprodução.** POST no formulário de lançamento com `valor_1 = "NaN"`:

```
ValueError: not enough values to unpack (expected 2, got 1)
  views_web.py:617  f"Débitos ({_valor_ptbr(total_debito)}) e créditos "
  views_web.py:129  parte_inteira, parte_decimal = texto.split(".")
```

Comparei os **mesmos 17 textos** pela tela e pela API. A API recusa **todos** com 400. A tela derruba em 8:

| valor digitado | TELA | API |
|---|---|---|
| `NaN`, `nan`, `-NaN` | **500** `ValueError` | 400 |
| `sNaN`, `Infinity`, `inf`, `-Infinity`, `1e500` | **500** `InvalidOperation` | 400 |

O caso de `Infinity` é o mais revelador: `Decimal("Infinity") == Decimal("Infinity")` é `True`, então `totais_batem` fica `True`, `criar_lancamento` é chamado e **recusa corretamente** (`para_decimal` rejeita infinito) — e a tela então derruba ao renderizar a recusa. **A validação de domínio funciona; a tela quebra enquanto conta ao usuário que funcionou.**

**Impacto, em linguagem de contador.** O Fred cola um valor de uma planilha cuja célula deu erro, clica em Gravar e recebe uma página de erro do servidor. Não há mensagem, não há caminho de volta, e — o pior — **ele não sabe se o lançamento foi gravado ou não**. A reação natural é clicar de novo, que é exatamente o cenário para o qual a chave de idempotência existe; e ela se perde junto com a página.
Verifiquei: nada é gravado em nenhum dos 8 casos. Mas a tela não diz isso.

**Correção recomendada.** `_valor_ptbr` deve recusar não‑finitos antes de formatar (ou `_decimal_do_formulario` deve rejeitar `Decimal` não finito e devolver erro de formulário, como já faz para texto malformado). O caminho mais barato e mais alinhado a DE‑026 é `_decimal_do_formulario` delegar a `apps.contabilidade.monetario.para_decimal` o **texto bruto**, em vez de construir o `Decimal` por conta própria — ver achado 2.
**Como verificar:** teste parametrizado com os 8 textos acima, exigindo status 400 (não 500) e mensagem de campo. Responsável: `especialista-frontend`, com `desenvolvedor-pleno` se a correção descer para `monetario.py`.

### 2 — MÉDIA · A tela grava quatro formatos de valor que a API recusa de propósito

**Requisito:** AGENTS.md §8 ("evitar duplicação de regras entre tela, API…"); DE‑026; DE‑010 e os achados 6/7 da auditoria anterior, que estabeleceram um formato decimal **textual** estrito.
**Local:** `/home/user/DataLedger/apps/contabilidade/views_web.py:391-406` (`_decimal_do_formulario`).

**Medição.**

| valor digitado | TELA | API | gravado pela tela como |
|---|---|---|---|
| `1e3` | **302 gravou** | 400 | `1.000,00` |
| `1_000` | **302 gravou** | 400 | `1.000,00` |
| `+10,00` | **302 gravou** | 400 | `10,00` |
| `10,00 ` (espaço final) | **302 gravou** | 400 | `10,00` |

O docstring de `_decimal_do_formulario` afirma: *"A validação de DOMÍNIO (sinal, escala máxima — DE‑010) continua sendo feita só por `criar_lancamento`"*. Isso é verdade para sinal e escala. Mas ao converter o texto para `Decimal` **dentro da view**, a função retira de `para_decimal` a única coisa que só ele podia fazer: julgar o **formato textual**. `criar_lancamento` recebe um `Decimal` já pronto e não tem mais o que recusar.

**Impacto.** A tela é uma porta mais frouxa que a API para a mesma invariante — é o risco central que o plano nomeia ("duplicar a regra") invertido: não é uma cópia divergente, é um guarda **contornado**. `1e3` virar 1.000,00 num lançamento é uma reinterpretação silenciosa de mil vezes o que está escrito na tela.
**Correção:** passar o texto (já com a vírgula convertida) a `para_decimal` e traduzir `ValorMonetarioInvalido` em erro de formulário.
**Como verificar:** teste que afirme, para a mesma lista de textos, o **mesmo** veredito na tela e na API. Responsável: `especialista-frontend`.

### 3 — ALTA · O rodapé "Total conferido antes de gravar" mostra `0,00` com as linhas preenchidas na mesma página

**Requisito:** critério 10 ("a tela mostra o total de débitos e o de créditos").
**Local:** `/home/user/DataLedger/apps/contabilidade/views_web.py:506-515` (o ramo `acao == "adicionar_linha"` chama `_contexto_form_lancamento` **sem** `total_debito`/`total_credito`), com `/home/user/DataLedger/templates/contabilidade/lancamento_form.html:91-92` (`|default:"0,00"`).

**Reprodução.** POST com `acao=adicionar_linha`, linha 1 débito `1.500,00`, linha 2 crédito `1.500,00`. HTTP **200**, sem erro:

```
rodapé:                    ['0,00', '0,00']
value dos campos de valor: ['1.500,00', '1.500,00', '', '', '']
```

**Impacto.** Esta é a única tela cuja função declarada é *"conferir o total antes de gravar"*, e é a única forma de ver o total num caminho que não seja uma recusa — porque não há JavaScript (por decisão, critério 15) e não existe botão "Conferir". Um contador que acrescenta uma linha e olha o rodapé lê **débito 0,00, crédito 0,00**: ou conclui que o sistema perdeu o que ele digitou, ou conclui que os totais estão batendo (zero igual a zero) e manda gravar. Não é número errado no livro — é número errado no lugar onde o Fred vai confiar, com aparência de certo e HTTP 200. Exatamente o caso que o enunciado desta auditoria chama de pior que uma API errada.

**Correção.** O ramo `adicionar_linha` deve calcular e passar os dois totais (as linhas já estão no POST), ou o rodapé deve dizer explicitamente "total ainda não conferido" quando não houver total, em vez de `0,00`. A primeira opção é melhor: transforma o botão "Adicionar linha" no botão de conferência que a tela não tem.
**Como verificar:** o teste que escrevi — POST `acao=adicionar_linha` com linhas preenchidas, extrair o `<tr class="linha-total">` e comparar com a soma dos `value` dos campos de valor. Responsável: `especialista-frontend`.

### 5 — MÉDIA · Partidas além da vigésima são descartadas em silêncio, e o lançamento é gravado como sucesso

**Requisito:** AGENTS.md §8 ("não deixar funcionalidades incompletas apresentadas como prontas"), §10 (memória de cálculo rastreável).
**Local:** `/home/user/DataLedger/apps/contabilidade/views_web.py:489` (`num_linhas = max(2, min(num_linhas, LINHAS_MAXIMAS_LANCAMENTO))`) e `:409-427` (`_linhas_lancamento_do_post` itera só até `num_linhas`).

**Reprodução.** POST com `num_linhas=22`, 22 partidas em que as 20 primeiras batem (10×10,00 débito / 10×10,00 crédito) e as duas últimas também (77,00 / 77,00):

```
status: 200 (após redirect) — "Lançamento gravado com sucesso"
lançamentos: 1    partidas: 20    soma de débito: 100.00   (enviado: 177,00)
nenhuma mensagem contendo "limite", "máximo" ou "descartado"
```

**Impacto.** Escrituração **parcial e balanceada**: 77,00 de débito e 77,00 de crédito desaparecem, o lançamento fecha, e nenhuma conferência o aponta — nem a de lotes desbalanceados (ele está balanceado), nem o balancete (o total é consistente com o que foi gravado). ### 6 — MÉDIA · A indentação hierárquica nunca é aplicada: o `float` localizado gera CSS inválido

**Requisito:** plano DL‑017, riscos ("Nenhum `float` em nenhum ponto") e a promessa da fase B ("Plano de contas: lista **hierárquica**"); critério 14 (HTML válido).


`padding-left: 1,25rem` é declaração CSS inválida. Medido no Chromium (`/opt/pw-browsers/chromium-1194/chrome-linux/chrome --headless`, `getComputedStyle`):

```
n1=1px | n2=1px | n3=1px | ok=40px
```

Ou seja: as três variantes com vírgula caem no padrão da tabela (1 px) e a de controle com ponto dá 40 px. **Nenhuma conta é indentada, em nenhum nível, em nenhuma das duas telas.** Nenhum teste falha, nenhum erro aparece.

**Impacto.** O plano de contas e o balancete são listas hierárquicas sem hierarquia visível. A informação de nível ainda existe na coluna "Nível", então ninguém lê número errado — mas a única pista visual de estrutura, que é o que faz um plano de contas de quatro níveis ser legível, simplesmente não está lá. **Correção:** usar `Decimal` ou inteiro (múltiplos de 125 centésimos, ou classe CSS `nivel-N`), ou envolver com `|unlocalize`/`|stringformat`. Classe CSS é o melhor: tira o estilo inline (que também é atrito para CSP).
**Como verificar:** teste que extraia todo `style="padding-left: …"` do HTML e recuse vírgula; complementarmente, medir `getComputedStyle` no Chromium. Responsável: `especialista-frontend`.

### 10 — BAIXA · As colunas consolidadas do balancete ficam sem total, ao lado de um rodapé que totaliza outras duas

**Requisito:** critério 6 (atendido); DE‑024 §2. É legibilidade, não aritmética.

**Medição.** Plano de três níveis, um único lançamento de 1.000,00:

```

rodapé "Total do período" ........................ 1000.00
```

**Impacto.** Num balancete de verificação, a coluna "Débitos" é a coluna que um contador soma — é o gesto que o plano descreve como "o que um contador faz com um balancete na frente".
