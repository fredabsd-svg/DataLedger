## 3. Análise técnica

### 3.1 Migration

```python
operations = [
    migrations.AddConstraint(
        model_name="lancamentocontabil",
        constraint=models.CheckConstraint(
            condition=models.Q(empresa_id__isnull=False),
            name="ck_lancamentocontabil_empresa_not_null",
        ),
    ),
]
```

**Veredicto:** ✅ Sintaxe correta. Django 5/6 gera `ALTER TABLE ... ADD CONSTRAINT ck_lancamentocontabil_empresa_not_null CHECK (empresa_id IS NOT NULL)`. Idempotente em caso de re-run (Django nomeia a constraint, então re-aplicar falharia com nome duplicado — comportamento padrão e aceitável).

### 3.2 Cobertura de testes

A iteração da F6 produziu um achado interessante durante a auditoria:

- **1ª tentativa (1f170bd)**: teste afirmava que o INSERT direto com NULL levantaria `IntegrityError` mencionando `ck_lancamentocontabil_empresa_not_null`. A CI reprovou porque o PG avalia `NOT NULL` da coluna **antes** de CHECK constraints — então a mensagem de erro vem do NOT NULL, não do CHECK.
- **2ª tentativa (1ddbcb9)**: corrigiu CNPJ (varchar(14)), mas o problema da mensagem continuava.
- **3ª tentativa (38163e8)**: reescrita dos testes para refletir a realidade do PG:
  - Teste #2 aceita AMBAS as mensagens (`violates not-null constraint` OU `ck_lancamentocontabil_empresa_not_null`) — reconhece que o NOT NULL é a primeira linha de defesa.
  - Teste #3 simula o cenário de bypass documentado no DE-051 (`ALTER TABLE DROP NOT NULL` + INSERT NULL) e verifica que o CHECK pega com mensagem mencionando `ck_lancamentocontabil_empresa_not_null`. Este teste **prova que a CHECK constraint faz o trabalho prometido** no DE-051.

**Achado positivo (A1)**: a iteração dos testes na F6 capturou um detalhe importante de implementação do PostgreSQL (ordem de avaliação NOT NULL → CHECK) que não estava documentado no plano original. O teste #3 é **mais rigoroso** que o teste original, e cobre o cenário de bypass que o DE-051 realmente defende.

### 3.3 Riscos

| Risco | Severidade | Mitigação |
|-------|------------|-----------|
| CHECK constraint não-regenerada no primeiro deploy Python 3.12+ | Baixo | Migration é hand-written; CI valida com `makemigrations --check --dry-run` antes do merge |
| Teste #3 polui schema se assertion falhar | Mitigado | try/finally garante `SET NOT NULL` de volta |
| Falsos positivos em outros testes durante a janela do teste #3 | Baixo | TestCase usa transação por teste (rollback no tearDown), mas o `ALTER TABLE` no nível do banco **não é revertido pelo transaction.atomic do TestCase** — daí a importância do try/finally |
| PG avaliar NOT NULL antes de CHECK | Mitigado | Teste #3 cobre o cenário de bypass; mensagem de erro é informativa o suficiente |
